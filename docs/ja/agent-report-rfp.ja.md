# RFP: agent-report

> 作成日: 2026-10-30
> 状態: Draft

## 1. 課題

gem-agent と lagent を使う第三者が不具合や改善を報告するとき、開発側には相手の環境の規模（ツール数・コンテキスト量・セッションの長さ）や使い方を知る手段がない。相手のセッション記録には業務データが含まれるので、そのままでは渡せない。agent-report は、手元のセッション記録を読むだけで決まった項目の数字を作り、本人が中身を確かめてから報告に添えられるようにする。主な利用者は両ランタイムの外部利用者で、開発者自身が自分の利用を測り直す用途にも使う。

## 2. 機能仕様

### コマンド

```
agent-report [--runtime gem-agent|lagent|all] [--since <期間>] [--json]
             [--mcp-names] [--sessions-dir <path>]
```

| フラグ | 既定 | 意味 |
|---|---|---|
| `--runtime` | `all` | 集計するランタイム |
| `--since` | `30d` | 集計期間（`30d`・`2026-09-01`・`all`） |
| `--json` | オフ | 人が読める表の代わりに JSON を出す |
| `--mcp-names` | オフ | MCP サーバー名ごとの回数を出す（Phase 2） |
| `--sessions-dir` | 各ランタイムの既定 | 記録の場所を変える（`--runtime` が 1 つのときだけ） |

既定の記録の場所:

- gem-agent: `~/.local/state/gem-agent/sessions`
- lagent: `~/.local/state/lagent/sessions`

### 入出力

- **入力**: 上記ディレクトリ配下の JSONL のセッション記録（schema 2）。読むだけで、書き込み・移動・削除はしない。
- **出力**: stdout。表と JSON は同じ集計結果から作るので、表で確かめた中身と JSON の中身は一致する。
- **出す項目**（ランタイムごと。すべて記録に書かれている事実から作る）:
  - 集計期間、セッション数、ヘッダに現れた版数とモデル名
  - ターンあたりのラウンド数の分布
  - セッションあたりの最大プロンプトトークン、キャッシュ率、会話圧縮の回数
  - 組み込みツールごとの呼び出し回数と所要時間（p50 / p90 / 最大）
  - シェルのレーン別回数、タイムアウトの回数
  - 承認の判断の内訳（操作者 / 自動、承認 / 拒否、段階）
  - ラウンド上限での介入回数、モード切替の回数
  - MCP の呼び出し回数、サーバー数、ツール数
  - 未知の記録の種類の件数、読めなかった行の件数
- **出さないもの**: 会話本文、コマンド、パス、宣言された目的、通知文、エラー文など、記録中の自由記述は一切出さない。組み込みツール名はランタイムごとの既知の一覧と照合し、一覧にない名前は「その他」に数える。MCP の名前は `--mcp-names` を付けたときだけ出す。
- **記録にない事実**: 起動の仕方（`-p`・`--auto`・`--allow` など）はランタイムが記録していないので「記録なし」と出す。

### 設定

設定ファイルは持たない。すべてフラグで指定する。

### 外部依存

なし。Go 標準ライブラリのみ。ネットワークに出ない。

## 3. 設計判断

- **Go・標準ライブラリのみ**: 署名と公証を済ませた単一バイナリなら、第三者も中身の分からないスクリプトを実行せずに済む。依存を持たないことでサプライチェーンの面も増やさない。
- **ランタイムの外に置く**: gem-agent の ADR-0061 は分析をランタイムの外に置くと定めている。また、集計する道具が集計対象を変えることはしない。対象が記録していない事実は「記録なし」として扱い、対象に記録を足して埋めない。
- **送信しない**: 受け取りサーバーは作らない。一人運営で公開の受け口を守る負担、誰でも偽のデータを送り込める問題、セキュリティ用途の利用者にとって外へ勝手に送る道具は信頼を損なう、の 3 点が理由。渡すのは本人が行う。
- **決まった項目の数字だけ**: 何を伏せるかの規則を作ると、規則が際限なく増え続ける。最初から数字と既知の名前だけに絞れば、その規則がいらない。
- **gem-usage-lens とは別のツール**: gem-usage-lens は自分の費用を見る道具で、こちらは第三者が報告に添える道具なので、使う人も目的も違う。記録を読む処理は共有ライブラリにせず書き直す。共有すると、片方の都合で両方を同時にリリースしなければならなくなる。
- **記録形式の違いに耐える**: ヘッダの schema を確かめ、知らない記録の種類は数えたうえで飛ばす。組み込みツール名はランタイムごとに既知の一覧を持つ。
- **スコープ外**: 送信と受け取りサーバー、ランタイムへの変更、Claude Code の記録、費用の計算（gem-usage-lens の領分）、GUI、自由記述の出力、設定ファイルの読み取り（Phase 2 で必要が見えたときに再検討）。

## 4. 開発計画

### Phase 1: 中核

- 両ランタイムの記録の読み取り、集計、表と JSON の出力、`--runtime` / `--since` / `--sessions-dir`
- テストは合成した記録だけで書く。実データはリポジトリに入れない
- 開発者自身の記録で実行し、2026-10-30 の集計スクリプトと数字が一致するかを確かめる

### Phase 2: 追加機能

- `--mcp-names`（実装が小さいため Phase 1 に前倒しで含めた）
- 設定ファイルの読み取りは、Phase 1 の出力を実際の報告に使ってみて必要が見えた場合だけ、項目を決めて足す

### Phase 3: リリース

- README（日英）、CHANGELOG、AGENTS.md
- リリース前の独立検証（サブエージェント）
- 署名・公証したリリース、homebrew tap、util-series への統合
- gem-agent と lagent の README に「報告時はこの出力を添えてください」と案内する件は、それぞれのプロジェクトに issue で依頼する

Phase 1 と Phase 2 は、それぞれ単独でレビューできる。

## 5. 必要な API スコープ・権限

なし。読むのは利用者自身のホームディレクトリ配下のファイルだけ。

## 6. シリーズ

Series: util-series
Reason: 手元のデータを読んで集計する lens 系の道具（gem-usage-lens・claude-usage-lens など）がすでに util-series にある。外部サービスのクライアントではないので cli-series には当たらない。

## 7. 外部プラットフォームの制約

外部サービスはない。制約は次の 2 つ。

- **記録形式**: lagent は記録と使用量記録の形式を安定性の約束に含めている（lagent ADR-0023）。gem-agent は記録形式を約束に含めるか文書に明記していない。agent-report は gem-usage-lens に続いて 2 つ目の利用者になる。形式を約束に含めるかは gem-agent 側の判断なので、必要になれば issue で依頼する。
- **配布は darwin/arm64 のみ**: 両ランタイムが macOS 専用なので合わせる。util-series の標準（4 種）からの例外として、統合時にシリーズの CLAUDE.md に記載する。

## 議論の記録

- **発端（2026-10-30）**: gem-agent を自律実行の基盤として拡張する企画 6 件を出し、利用者の判断で先に頻度を測った。手元のセッション記録を読むだけの集計では、編集ジャーナル・バックグラウンドジョブ・並列実行の 3 件に根拠が出なかった。10 月の実利用は 1 セッションだった。
- **何が足りないか**: 最初は「利用状況を計量する機能が足りない」と考えた。調べると gem-agent には監査用の計測（ADR-0035）があり、Cloud Logging への送信も有効だった。足りないのは蓄積先と起動の仕方の記録だった。続いて利用者が論点を絞った。足りないのは、まったくの第三者からデータを提供してもらう手段である。
- **第三者の規模**: リリースのダウンロード数は 146 リリースで 429 回、最近は 1 リリースあたり 3〜6 回（自分の検証分を含む）。スターは 0、issue は自分の起票のみ。外部からの報告は GitHub 以外の経路で届いている。統計としての価値より、手元では再現しない環境の事実（ある外部運用者ではツール 367 個・13 万トークン）に価値がある。
- **退けた案**:
  - gem-agent に統計のサブコマンドを入れる: 分析をランタイムの外に置く方針（ADR-0061）に反する。利用者の提案で別ツールにした。
  - 開発側へ自動送信する: 理由は §3「送信しない」のとおり。
  - gem-usage-lens に統合する: 使う人と目的が違う。
  - ランタイムに記録を足して欠けを埋める: 集計する道具が対象を変えることになる。agent-activity-lens の中止で得た教訓。
- **利用者の決定**: 名前は agent-report。lagent も対象に含める。MCP 名は指定時だけ出す。Phase 1 は記録だけを読む。既定の期間は直近 30 日。配布は darwin/arm64 のみ。
- **使われる場面**: ふだんの提供依頼では使われない（agent-board の前例）。報告する場面に結び付け、各ランタイムの README と issue テンプレートから案内する。
