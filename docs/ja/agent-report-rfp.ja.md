# RFP: agent-report

> 作成日: 2026-10-30
> 状態: Draft

## 1. 課題

gem-agent と lagent を使う第三者が不具合や改善を報告するとき、開発側には相手の環境の規模（ツール数・コンテキスト量・セッションの長さ）や使い方を知る手段がない。相手のセッション記録には業務データが含まれるので、そのままでは渡せない。agent-report は、手元のセッション記録を読むだけで決まった項目の数字を作り、本人が中身を確かめてから報告に添えられるようにする。主な利用者は両ランタイムの外部利用者で、開発者自身が自分の利用を測り直す用途にも使う。

## 2. 機能仕様

### コマンド

```
agent-report [--runtime gem-agent|lagent|all] [--since <期間>] [--json]
             [--mcp-names] [--sessions-dir <path>]
```

| フラグ | 既定 | 意味 |
|---|---|---|
| `--runtime` | `all` | 集計するランタイム |
| `--since` | `30d` | 集計期間（`30d`・`2026-09-01`・`all`） |
| `--json` | オフ | 人が読める表の代わりに JSON を出す |
| `--mcp-names` | オフ | MCP サーバー名ごとの回数を出す（Phase 2） |
| `--sessions-dir` | 各ランタイムの既定 | 記録の場所を変える（`--runtime` が 1 つのときだけ） |

既定の記録の場所:

- gem-agent: `~/.local/state/gem-agent/sessions`
- lagent: `~/.local/state/lagent/sessions`

### 入出力

- **入力**: 上記ディレクトリ配下の JSONL のセッション記録（schema 2）。読むだけで、書き込み・移動・削除はしない。
- **出力**: stdout。表と JSON は同じ集計結果から作るので、表で確かめた中身と JSON の中身は一致する。
- **出す項目**（ランタイムごと。すべて記録に書かれている事実から作る）:
  - 集計期間、セッション数、ヘッダに現れた版数とモデル名
  - ターンあたりのラウンド数の分布
  - セッションあたりの最大プロンプトトークン、キャッシュ率、会話圧縮の回数
  - モデルごとの呼び出し数とトークン数
  - 主ループのモデル呼び出しを 1 回ずつ見たもの: 1 回ごとの待ち時間、再試行で失った時間、そして「プロンプトの大きさ別」「プロンプトが作り直された理由別」「前の呼び出しが終わってから・始まってからの時間別」の、呼び出し数・プロンプトとキャッシュのトークン数・キャッシュに当たった回数・待ち時間
  - モデル呼び出しのバックオフ再試行のステータス別・呼び出しの種類別・モデル別の件数と、それを記録するビルドのセッションが何件か
  - 組み込みツールごとの呼び出し回数と所要時間（p50 / p90 / 最大）。呼び出しの開始から数えたものと、最後の承認の判断から数えたものの両方
  - 承認プロンプトで操作者の回答を待った時間
  - 複数の呼び出しを含む応答の種類別（読み取りだけ / MCP・Web を含む / その他）の件数と、順に実行してかかった秒数・同時に実行した場合の秒数
  - シェルのレーン別回数、タイムアウトの回数
  - 承認の判断の内訳（操作者 / 自動、承認 / 拒否、段階）
  - ラウンド上限での介入回数、モード切替の回数
  - MCP の呼び出し回数、サーバー数、ツール数
  - 未知の記録の種類の件数、読めなかった行の件数
- **出さないもの**: 会話本文、コマンド、パス、宣言された目的、通知文、エラー文など、記録中の自由記述は一切出さない。組み込みツール名は両ランタイム共通の既知の一覧と照合し、一覧にない名前は「その他」に数える。MCP の名前は `--mcp-names` を付けたときだけ出す。
- **記録にない事実**: 起動の仕方（`-p`・`--auto`・`--allow` など）はランタイムが記録していないので「記録なし」と出す。

### 設定

設定ファイルは持たない。すべてフラグで指定する。

### 外部依存

なし。Go 標準ライブラリのみ。ネットワークに出ない。

## 3. 設計判断

- **Go・標準ライブラリのみ**: 署名と公証を済ませた単一バイナリなら、第三者も中身の分からないスクリプトを実行せずに済む。依存を持たないことでサプライチェーンの面も増やさない。
- **ランタイムの外に置く**: gem-agent の ADR-0061 は分析をランタイムの外に置くと定めている。また、集計する道具が集計対象を変えることはしない。対象が記録していない事実は「記録なし」として扱い、対象に記録を足して埋めない。
- **送信しない**: 受け取りサーバーは作らない。一人運営で公開の受け口を守る負担、誰でも偽のデータを送り込める問題、セキュリティ用途の利用者にとって外へ勝手に送る道具は信頼を損なう、の 3 点が理由。渡すのは本人が行う。
- **決まった項目の数字だけ**: 何を伏せるかの規則を作ると、規則が際限なく増え続ける。最初から数字と既知の名前だけに絞れば、その規則がいらない。
- **gem-usage-lens とは別のツール**: gem-usage-lens は自分の費用を見る道具で、こちらは第三者が報告に添える道具なので、使う人も目的も違う。記録を読む処理は共有ライブラリにせず書き直す。共有すると、片方の都合で両方を同時にリリースしなければならなくなる。
- **記録形式の違いに耐える**: ヘッダの schema を確かめ、知らない記録の種類は数えたうえで飛ばす。組み込みツール名は両ランタイム共通の既知の一覧を 1 つ持つ（両者が宣言する名前はほぼ重なっており、分けても相手側にしかない名前が「組み込み」から「不明」へ移るだけ）。
- **スコープ外**: 送信と受け取りサーバー、ランタイムへの変更、Claude Code の記録、費用の計算（gem-usage-lens の領分）、GUI、自由記述の出力、設定ファイルの読み取り（Phase 2 で必要が見えたときに再検討）。

## 4. 開発計画

### Phase 1: 中核

- 両ランタイムの記録の読み取り、集計、表と JSON の出力、`--runtime` / `--since` / `--sessions-dir`
- テストは合成した記録だけで書く。実データはリポジトリに入れない
- 開発者自身の記録で実行し、2026-10-30 の集計スクリプトと数字が一致するかを確かめる

### Phase 2: 追加機能

- `--mcp-names`（実装が小さいため Phase 1 に前倒しで含めた）
- 設定ファイルの読み取りは、Phase 1 の出力を実際の報告に使ってみて必要が見えた場合だけ、項目を決めて足す
- 承認待ちを除いた実行時間、プロンプトでの操作者の待ち時間、複数の呼び出しを含む応答の種類（2026-11-03 追加。議論の記録を参照）
- 主ループのモデル呼び出しを 1 回ずつ見たもの、モデルごとのトークン数、再試行（2026-11-13 追加。議論の記録を参照）

### Phase 3: リリース

- README（日英）、CHANGELOG、AGENTS.md
- リリース前の独立検証（サブエージェント）
- 署名・公証したリリース、homebrew tap、util-series への統合
- gem-agent と lagent の README に「報告時はこの出力を添えてください」と案内する件は、それぞれのプロジェクトに issue で依頼する

Phase 1 と Phase 2 は、それぞれ単独でレビューできる。

## 5. 必要な API スコープ・権限

なし。読むのは利用者自身のホームディレクトリ配下のファイルだけ。

## 6. シリーズ

Series: util-series
Reason: 手元のデータを読んで集計する lens 系の道具（gem-usage-lens・claude-usage-lens など）がすでに util-series にある。外部サービスのクライアントではないので cli-series には当たらない。

## 7. 外部プラットフォームの制約

外部サービスはない。制約は次の 2 つ。

- **記録形式**: lagent は記録と使用量記録の形式を安定性の約束に含めている（lagent ADR-0023）。gem-agent は記録形式を約束に含めるか文書に明記していない。agent-report は gem-usage-lens に続いて 2 つ目の利用者になる。形式を約束に含めるかは gem-agent 側の判断なので、必要になれば issue で依頼する。
- **配布は darwin/arm64 のみ**: 両ランタイムが macOS 専用なので合わせる。util-series の標準（4 種）からの例外として、統合時にシリーズの CLAUDE.md に記載する。

## 議論の記録

- **発端（2026-10-30）**: gem-agent を自律実行の基盤として拡張する企画 6 件を出し、利用者の判断で先に頻度を測った。手元のセッション記録を読むだけの集計では、編集ジャーナル・バックグラウンドジョブ・並列実行の 3 件に根拠が出なかった。10 月の実利用は 1 セッションだった。
- **何が足りないか**: 最初は「利用状況を計量する機能が足りない」と考えた。調べると gem-agent には監査用の計測（ADR-0035）があり、Cloud Logging への送信も有効だった。足りないのは蓄積先と起動の仕方の記録だった。続いて利用者が論点を絞った。足りないのは、まったくの第三者からデータを提供してもらう手段である。
- **第三者の規模**: リリースのダウンロード数は 146 リリースで 429 回、最近は 1 リリースあたり 3〜6 回（自分の検証分を含む）。スターは 0、issue は自分の起票のみ。外部からの報告は GitHub 以外の経路で届いている。統計としての価値より、手元では再現しない環境の事実（ある外部運用者ではツール 367 個・13 万トークン）に価値がある。
- **退けた案**:
  - gem-agent に統計のサブコマンドを入れる: 分析をランタイムの外に置く方針（ADR-0061）に反する。利用者の提案で別ツールにした。
  - 開発側へ自動送信する: 理由は §3「送信しない」のとおり。
  - gem-usage-lens に統合する: 使う人と目的が違う。
  - ランタイムに記録を足して欠けを埋める: 集計する道具が対象を変えることになる。agent-activity-lens の中止で得た教訓。
- **利用者の決定**: 名前は agent-report。lagent も対象に含める。MCP 名は指定時だけ出す。Phase 1 は記録だけを読む。既定の期間は直近 30 日。配布は darwin/arm64 のみ。
- **使われる場面**: ふだんの提供依頼では使われない（agent-board の前例）。報告する場面に結び付け、各ランタイムの README と issue テンプレートから案内する。
- **Phase 1 の確認（2026-10-30）**: 開発者自身の記録で動かし、集計スクリプトと突き合わせた数字はすべて一致した。gem-agent はツールを呼んだ応答 1821・複数呼び出し 42・シェル 497 とレーン別の内訳・タイムアウト 2・MCP 333、lagent はシェル 149・自動承認 46 / 人に回した数 460・承認プロンプトで 456 / 4・空応答 29。
- **独立検証（2026-10-30）**: 設計を固めた時点の検証は行っておらず、Phase 1 の後に設計時とリリース前の検証をまとめて実施した。サブエージェント 2 本で、1 本はランタイムの書き手に照らしたコードの正しさ、もう 1 本は組織の規約と教訓との突き合わせ。採用して直したもの: lagent のセッションの事実メッセージと両ランタイムの中断後の注記を操作者のターンに数えていた（lagent の実データでターンが約半分水増し）、`access` が文字列でないとメッセージごと失っていた、版数とモデル名のパターンが GCP のリソースパスやメールアドレスを通していた（版数はタグか `git describe` の出力、モデル ID は `/` が高々 1 つで `@` を含まないものに狭めた）、シンボリックリンクの記録置き場が空に見えた、読めないサブディレクトリを数えていなかった、タイムアウトの印を出力のどこでも拾っていた、記録の種類 2 つが未登録だった、`mode_start` をプロセスごとに数えていた、`/clear` は数えられない（`not_recorded` へ移した）、`--since` の境目で偽の異常が出た、読めない判断記録の数え違い、`not_recorded` に理由を書いた、時刻を UTC にした、存在しない `--sessions-dir` はエラーにした、README の状態表示を外し文書の節を追加、`.claude/` と実データの除外、`govulncheck` の追加。受け入れた残余: 利用者が自分で付けたモデル ID は書いたとおりに出る（README で、渡す前に `models` の節を確かめるよう案内）。リリース時に回すもの: CHANGELOG の `[0.1.0]` 節、darwin/arm64 の例外をシリーズ側に記録すること。
- **初めての第三者の報告（2026-11-03）**: ある利用者の v0.1.0 の報告（30 日分、gem-agent と lagent）は、開発者よりはるかに重い使い方を示した。gem-agent の応答の 42% が複数の呼び出しを含み、MCP の呼び出しは 5,766 回で中央値 9.5 秒、長い尾は最大 36 時間に及んだ。自律化の 6 企画のうち 2 件（操作者への通知、読み取り呼び出しの並列実行）は、この報告からは決められなかった。所要時間が承認プロンプトでの待ちと実行を混ぜており、複数の呼び出しを含む応答のどれが読み取りだけかも分からないためである。利用者の依頼で、最後の承認の判断から数える実行秒数、プロンプトでの操作者の待ち時間、複数の呼び出しを含む応答の種類別の件数と順に実行した秒数・同時に実行した場合の秒数を足した。読み取りだけかどうかはランタイム自身の `Mutating` の定めに従う（MCP と Web のツールはそこで変更ありとされているので、別の種類にした）。判断の記録が常に結果待ちの先頭の呼び出しを指すことは、開発者の記録で確かめた（gem-agent 1,179 件、lagent 1,041 件、例外なし）。食い違いは信じずに異常として数える。別に書いたスクリプトで手元の全記録を集計し直し、新しい数字はすべて一致した。
- **追加分の独立検証（2026-11-03）**: サブエージェント 1 本が、新しい項目を両ランタイムの書き込み処理と手元の記録に照らして確かめた。確認できたこと: 判断の記録は必ず応答とその呼び出しの結果の間に書かれ、結果待ちの先頭の呼び出しを指す。どの呼び出しにも結果がちょうど 1 件ある。読み取りだけの一覧は、ランタイムの `Mutating` の定めと履歴を通して一致する。新しい項目が自由記述を写すことはない。採用して直したこと: レーンを指定しないシェル実行は read レーンで動く（lagent は最初から、gem-agent は v0.69.0 から）ので、版数からレーンがあると分かる場合は読み取りとして数える。`ceiling_refused` を実行されなかった呼び出しとして扱う。文書は「中断した応答は数えない」としていたが、ランタイムはすべての呼び出しに（中断したものにはすぐ）結果を返すので、そうした呼び出しはほぼ 0 秒として数えると改めた。ワンショット実行はプロンプトで聞かずに拒否し、それを操作者の回答として記録することを明記した。`if_parallel_sec` はすべての呼び出しを同時に始められると仮定していることを明記した。v0.1.0 の欠陥として別に直したこと: `connection_lost` と `window_full` を未知の記録の種類に数えていた。受け入れた残余: 記録を残さない拒否（gem-agent のループ検知による省略、実行前の中断、不正な引数、未知の名前）は実行秒数にほぼ 0 秒で入る。承認の記録を伴わないダイアログ（読み取り専用の上限の解除）は次の操作者の待ちに含まれる。`ask_user` の実行秒数は操作者が答えるまでの時間である。
- **モデルの時間・キャッシュ・再試行（2026-11-13）**: 開発者から、gem-agent の時間と費用がどこに掛かっているかを問われた。開発者自身の記録を手で集計したところ（30 日分、テスト用ディレクトリを除く 5 セッション、主ループの呼び出し 215 回、ほぼ 1 つのモデル）、定価換算の費用の 88% がキャッシュから供給されなかったプロンプトのトークンで、呼び出しの間の時間が長いほどキャッシュに当たる割合が下がっていた。これは 1 つのアカウントの 1 か月分であり、何を数える価値があるかを示すもので、ほかでも成り立つことを示すものではない。開発者の利用は第三者に比べて小さいので、同じ集計を第三者が実行できる形にする必要がある。schema 1 に追加: `tokens_by_model`、`main_calls`（呼び出しごとの待ち時間、再試行で失った時間、そしてプロンプトの大きさ別・作り直しの直後・前の呼び出しからの時間別の表）、`retries`。`retries` 以外は、ランタイムが以前から書いている記録を読むので、既にある記録でそのまま使える。
- **再試行の記録と「ランタイムを変えない」規則（2026-11-13）**: 規則に関わるので、起きた順に書く。同じ調査の中の同じ日に、両方のプロジェクトを保守している開発者が、まず gem-agent に `model_retry` レコードを書かせると決め（gem-agent ADR-0116: gem-agent の記録ではレート制限の待ちと遅い応答を区別できず、2 つのモードは再試行を表示もしない）、続いて、この道具でそれを数えることを求めた。gem-agent の変更は gem-agent の中で、その設計記録のもとで行われ、v0.101.0 の次のリリースに入る。この道具はその記録を読むだけで、lagent には何も求めず、lagent については「記録なし」と報告する。この道具の `retries` は、その gem-agent のリリースが出るまで役に立たないので、この道具のリリースはその後になる。2 つの判断は数分違いで、同じ問いに答えるものである。これが規則を守っているのか曲げているのかは開発者が決めることで、ここにはどちらとも論じず、起きたとおりに書く。レコードから読み出すのは、HTTP ステータス（列挙値）、呼び出しの種類（usage レコードの閉じた集合）、モデル（モデル名のパターン）だけである。
- **追加分の独立検証（2026-11-14）**: この道具に 1 本、gem-agent の記録に 1 本のサブエージェントを当て、どちらにも「何が間違っているかを探す」ことを課した。この道具について: 独立に書いたスクリプトでの数え直しは、gem-agent 2,383 回・lagent 1,298 回の主ループの呼び出しで全行が一致した。つまりコードは文書の定義どおりで、指摘は定義そのものについてだった。採用したもの: (1)「間隔別」の表は呼び出し自身の終わりまでを測っていたので、遅い呼び出しが自分で後ろの行に入っていた — 呼び出しの開始までで測ると 199 回中 139 回が行を移った — うえに、文書がその行をキャッシュの空き時間として読んでいた。呼び出しの開始までを測る 2 つの表 `by_idle`・`by_prefix_age` に置き換え、README には、表が示すのは当たりと外れの分布であって理由ではないと書いた。(2) 待ち時間がラウンド上限のダイアログでの操作者の時間を含んでいたので、`round_intervention` で開始位置を動かす。(3) 新しいビルドで再開されたセッションを最初のヘッダで判定していたので、再開の記録の版数と、再試行の記録があること自体も数える。(4) 再試行を主ループの呼び出しにモデル名で結び付けていたが、枠を設定していなければ全呼び出しが同じ名前なので、レコードの source で結び付ける。(5) lagent はサーバーが件数を返さないときもキャッシュ数を 0 と書く（1,298 回中 919 回が、一度も件数を返さなかったモデルの呼び出し）。これを `not_recorded` に書いた。(6) 最初のテストは 26 個の改変のうち 12 個を見逃した。開始位置を動かす 2 つの記録が、仕込みの中で同じ時刻を共有していたためである。仕込みを書き直し、13 個の改変は 13 個とも検出されるようになった。限界として受け入れ、README に書いたもの: 記録を残さないツール一覧の変更、何も変わらなくても書かれる再読み込みの記録、最後の試行でも失敗して諦めた呼び出しが `main_calls` に入らないこと。
